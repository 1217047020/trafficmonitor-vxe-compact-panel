# 下一阶段选型：北通手柄与水月雨布丁耳机／充电仓
日期：2026-10-02（Asia/Shanghai）

> 历史选型报告，保留当时的判断和验证边界，不代表当前版本状态。手柄与布丁已接入主线，最新结果见 `beitong-controller.md`、`pudding-plugin.md` 与 `verification.md`。下述 `evidence/`、`upstream/` 为未公开的本地参考目录，不随仓库分发。

## 结论

按工作区原有设备记录，本报告比较 **北通鲲鹏20（BTP-KP20 系列）** 与 **MOONDROP Pudding／MD-TWS-056**；不把结论推广到全部手柄和耳机。

- **最快新增可用显示：优先验证手柄 XInput 档位。** 原生 API 与当前 C++ TrafficMonitor 插件契合，成功时无需后台程序、Qt、手机或新硬件。但它不是精确百分比；北通是否真实上报必须实测。
- **如果必须显示真实百分比：布丁公开协议依据更具体。** 新找到布丁专用库、Windows RFCOMM 传输实现、三路电量抓包示例，已有条件做只读验证，不必从零逆向官方 App。
- **“布丁左右耳”与“布丁仓实时电量”要分开验收。** 有上游仓94%的示例，也有仓返回0xFF的实测记录；无法据此保证合盖、离耳、关机时仍能实时读取。
- 推荐顺序：手柄标准接口短验证 → 有可信档位就接插件；若只有占位数据或坚持百分比，转布丁只读查询 → 验证仓更新条件 → 最后接任务栏显示。
- 本次只做调研、只读系统查询、源码检查和离线对拍；没有对耳机发送命令、配对、安装软件、运行第三方控制界面或改现用插件／任务栏配置。

## 2. 难度比较

| 目标 | 路径 | 开发难度 | 核心不确定性 |
|---|---|---|---|
| 北通高／中／低／空 | XInputGetBatteryInformation | 低，前提是可信上报 | 无线接收器可能呈现有线／未知／固定占位值 |
| 北通精确百分比 | WinRT BatteryReport／设备属性；失败后厂商HID协议 | 标准路径低，厂商路径中高 | 没有找到可直接套用到当前型号的公开电量查询命令 |
| 布丁左右耳百分比 | Classic Bluetooth RFCOMM／SPP + GAIA业务查询 | 中 | 连接、实际封包、分包与粘包、会话占用 |
| 布丁仓百分比 | 同上，按组件type=3解析 | 中，可靠性验证更重 | 仓何时可见、合盖是否停止更新、是否只得到缓存 |
| 任意蓝牙耳机仓通用支持 | 按型号分Provider | 高，不宜作为本轮目标 | 不同厂商的服务、协议、广播与可用时机不统一 |

“手柄更好做”仅指标准档位链路；不能承诺它比布丁的**精确百分比**更容易。

## 3. 手柄：新增技术资料与实际用途

### 3.1 Microsoft XInput 文档：最短生产路径

[XINPUT_BATTERY_INFORMATION](https://learn.microsoft.com/en-us/windows/win32/api/xinput/ns-xinput-xinput_battery_information)定义电池类型与EMPTY／LOW／MEDIUM／FULL四档，不提供0–100百分比。
[XInput版本](https://learn.microsoft.com/en-us/windows/win32/xinput/xinput-versions)说明 `xinput9_1_0.dll` 没有电量函数；优先系统 `xinput1_4.dll`。

落地：
1. 先确认在线，再读电池类型和档位。
2. 初版用“高／中／低／空”或分段图标，不把它伪装成25／50／75／100%。
3. 微软规范仅保证已知电池类型的无线设备档位有效。第三方接收器返回WIRED／UNKNOWN时，不能只看成功码就采信；必须与实际电量变化对照。
4. XInput槽位不是稳定设备身份。第一版可限制为单在线手柄；多手柄时要做设备关联。

### 3.2 Linux内核社区：直接命中此前接收器ID

[已合入的KP20D HID补丁](https://github.com/torvalds/linux/commit/bfff246b3a31cb45ec297ca5e2a77c1410b207ac)明确写出 **20DD:5159 为 Direct/HID 模式**，并描述Linux下未持续读取interrupt-IN会导致周期重枚举的问题。

用途：
- 不要把20DD:5159这个HID身份当成XInput模式的唯一识别依据。
- 每种实际连接／模式分别记录VID/PID、HID集合、驱动与XInput状态。
- 后续若HID抓包出现周期断连，可以将“读取／保活条件”纳入诊断。
- 这不是Windows修复方案，也不是电量协议；本次不发送切模式／保活请求。

[开发者邮件讨论](https://lkml.iu.edu/2608.0/02295.html)还区分20BC系列XInput身份与20DD Direct/HID身份，并讨论Microsoft OS descriptor请求。它有助于理解模式切换，不应照抄为电量查询。

### 3.3 WinRT BatteryReport 与 SDL：备用路径和实现参考

[Gamepad.TryGetBatteryReport](https://learn.microsoft.com/en-us/uwp/api/windows.gaming.input.gamepad.trygetbatteryreport?view=winrt-26100)可尝试获取电池报告；若报告缺失／容量字段为空，必须返回未知，不能强行生成百分比。是否适用于这只北通尚未实测。

[SDL3电源接口](https://wiki.libsdl.org/SDL3/SDL_GetGamepadPowerInfo)与[Windows XInput后端](https://github.com/libsdl-org/SDL/blob/main/src/joystick/windows/SDL_xinputjoystick.c)可参考热插拔、状态映射与未知处理。SDL是封装与驱动集合，不会凭空让未上报电量的手柄支持电量；现阶段不必为一个接口引入整套SDL。

### 3.4 当前已知项目里的复用限制

本地BatteryMonitor的XboxProvider有档位映射和WinRT路径，但：
- RawGameController路径硬编码筛选Microsoft VID=0x045E，不能直接视为北通支持。
- XInput路径把WIRED设备的BatteryLevel也映射出来；这比微软规范更宽，不能未经实测直接套用。
- 当前TrafficMonitor插件只有鼠标采集与鼠标Snapshot；新增手柄状态即可，不需要重建一个跨设备大框架。

本地核验文件：

- `traffic-plugin/plugin.cpp`
- `traffic-plugin/plugin_items.h`

## 4. 布丁：新增资料比旧计划具体得多

### 4.1 roxyyn0304/moondrop-gaia-protocol：本轮最有价值的新来源

[布丁专用协议库](https://github.com/roxyyn0304/moondrop-gaia-protocol)包含Kotlin编解码、Python串口Web测试界面及[逆向记录](https://github.com/roxyyn0304/moondrop-gaia-protocol/blob/341614b3ef4cdd98f0d525b1d0f943dbc070af5c/docs/MOONDROP_Pudding_逆向结果.md)。

上游记录固件3.5.2，给出以下电量请求／响应示例：

```text
TX  FF 04 00 02 00 1D 1A 01 01 02
RX  FF 04 00 06 00 1D 1B 01 01 64 02 64 03 5E
                                  左100 右100 仓94
```

**这些是上游样本，不是本机读数。**
- 组件ID：1左、2右、3仓；数据按(ID, level)对解码，合法电量0–100。
- Windows可以先走系统已分配的蓝牙SPP出站COM串口验证，不一定从复杂WinRT代码起步；若无COM口，再用原生RFCOMM socket。
- Python `webtest.py` 依赖pyserial；整个界面含控制命令，不能当成只读探针直接启动。
- README声称MIT，但仓库树未见独立LICENSE文件；复制代码前应核对具体授权边界。

重要坑：README／逆向说明顶部把Len说成“feature+cmd+payload”，但源码编码与实际示例都是**payload长度**。本次离线执行纯编码函数，`01 02`生成Len=2而非4。实现时优先核对真实流与源码，不按标题说明机械照抄。

### 4.2 TWS-Pods-PC：Windows传输层参考，不是布丁仓成品

[Windows项目](https://github.com/Zhaoyi-ya/TWS-Pods-PC)通过ctypes调用 `ws2_32.dll` 建立RFCOMM，并含设备枚举、协议和会话代码。
[水月雨协议文档](https://github.com/Zhaoyi-ya/TWS-Pods-PC/blob/3350f424c1ab69c4bc6cff92dd7b603fb0025db2/moondrop/PROTOCOL.md)明确：现有解析仅左右耳，不含仓；该品牌握手仍待实机验证。

本次用它的原版Decoder／parse_battery_state离线解析：
- 左右两对：成功。
- 左右+仓94%：返回None。
- 左右+仓0xFF：也返回None。

原因：解析器只取payload最后4字节并要求为 `01 LL 02 RR`；一旦末尾追加仓，左右耳也一起丢失。
因此只借鉴Windows传输方式；不能直接用它的电量模型或将其作为布丁已适配的证据。GPL-3.0-only，复制实现需考虑项目许可。

### 4.3 MiuixMoondrop：组件解析、缺项与无数据状态

[协议说明](https://github.com/huime180/MiuixMoondrop/blob/2f78f6740b2f30d1c28d75ba05badb98b2eeb687/PROTOCOL.md)与[BatteryCodec](https://github.com/huime180/MiuixMoondrop/blob/2f78f6740b2f30d1c28d75ba05badb98b2eeb687/app/src/main/java/moe/huime/miuixmoondrop/core/BatteryCodec.kt)给出了实测相关边界：
- 布丁样本 `01 62 02 64 03 FF`：左98%、右100%，仓无数据。
- 先查询支持的电池，再读组件；但不能单凭支持列表不含3就断言永远没有仓值，上游另一条查询左右的样本仍附带了仓。
- 按组件ID解码，不按固定位置；一个组件不可用不能使其他组件丢失。

可以复用思路，**不照搬其缓存和显示语义**：
- 左右耳／仓各自记录有效采样时间，耳机新回包不能刷新旧仓时间。
- 重复收到相同有效电量也必须更新采样时间，不能只在数值变化时更新时间。
- 新回包只有左右耳时，仓可作为带时间的“上次记录”，不能冒充实时。
- 0xFF映射为未知／不可用，不是0%、255%、100%，也不单凭它断言物理仓已离线。
- 系统单值电量不复制成“独立左耳／右耳”假读数。
- 充电标志未实测，不从连接／有线状态猜。
- 裸PDU按下一帧标志切割存在歧义：0xFF本身就可能是仓无数据值，必须用实际封装与流样本验证。

### 4.4 FxxkMoondrop、Mooncontroller、MOONDROP-Pods：补充而非多份独立证明

- [FxxkMoondrop适配记录](https://github.com/bqj6666/FxxkMoondrop/blob/main/ADAPTATION.md)：能力探测、不同传输、模式差异与联调坑。
- [Mooncontroller](https://github.com/guwen777/Mooncontroller)：普通Android应用形态，便于作为手机对照；其布丁状态写“应该支持”，不是本机验证结论。
- [MOONDROP-Pods](https://github.com/roxyyn0304/MOONDROP-Pods)：SPP收发接线、通信日志与三路UI。
- [SpaceTravel-Protocol](https://github.com/pubglite55/SpaceTravel-Protocol)：可供后续查GAIA官方App实现，但不是布丁协议的直接替代。

它们存在fork／共同协议来源，不能数项目数量来提高可信度。PuddingPods仍是已知基础资料；新库的具体布丁样本和Miuix的无数据样本才是本轮新增的关键证据。

### 4.5 Microsoft蓝牙文档：不用ESP32也有原生路线

[Win32 Bluetooth connect](https://learn.microsoft.com/en-us/windows/win32/bluetooth/bluetooth-and-connect)支持依据服务UUID走RFCOMM连接。
[Windows RFCOMM指南](https://learn.microsoft.com/en-us/windows/apps/develop/devices-sensors/send-or-receive-files-with-rfcomm)可用于WinRT路线。
布丁候选SPP UUID：`00001101-0000-1000-8000-00805F9B34FB`。

建议：先COM／WinSock只读小探针验证，再做C++生产Provider；不优先安装PyBluez、不扫描整个蓝牙空间、不购置ESP32、不要求手机常驻桥接。标准GATT Battery Service仅适用于设备实际暴露该服务的情况；不能把BLE通用电量当成布丁仓电量。

## 5. 下一步的最小验收

### A. 手柄短验证，优先做

1. 按日常模式让手柄无线在线，USB线拔掉；用上述只读脚本查四槽。
2. 记录模式、身份、State返回、电池类型／档位与官方可见电量。
3. 若有可信档位，验证充电前后／不同电量状态和关机、重连；始终固定FULL或WIRED占位不算成功。
4. 若无有效上报，尝试实际蓝牙XInput模式与BatteryReport／目标属性，不盲发未知HID查询。
5. 档位可用就新增独立手柄插件项目；精准百分比无证据时不继续深挖到复杂厂商协议，优先转布丁。

### B. 布丁：先三路原始回包，不先做UI

1. 查看目标设备是否暴露SPP服务／出站COM口，不断开现有音频，不启动带写设置的第三方UI。
2. 单独实现串流读取与已知电量查询；超时、错误和拆包需有原始流记录。
3. 对照官方App／可靠手机工具，在相同物理状态下核对左右耳／仓；对照工具若只显示旧值不作为真值。
4. 一次只改变一个状态：开盖双耳在仓 → 合盖 → 单耳取出 → 双耳取出 → 仓充电 → 断连重连。记录仓字段出现、变化、缺失和0xFF。
5. 至少两个实际电量状态、重启探针后可重复成功，才接TrafficMonitor。

耳机上线后可以先增加“耳机电量”独立项；紧凑面板扩宽／轮换由用户确认，不直接改现用9pt、双行三列布局。
